# Hackathon Quickstart

This is the fast path for a 4–8 hour frontend sprint. Speed comes from making fewer wrong turns, not from removing the concept gate or QA.

## Before coding — 15 minutes

Copy the repository into the project context. Complete the project brief and asset/icon brief. State the product truth, primary user, core workflow, emotional premise, technical boundaries, and what must not change. Add three to seven references, each with one strength to study and one boundary not to copy.

## Art direction — 20 minutes

Ask the agent to propose one recommended visual world and two alternatives. Require a short comparison using the scorecard. Do not spend an hour making three full websites; make enough of the landing hero and core workflow to judge composition, type, palette, material, metaphor, and product relationship.

## Two-surface proof — 60 to 90 minutes

Build the entry surface and one real workflow first. Use the real product language and the real states that matter. Capture desktop and mobile screenshots. Reject immediately if the landing page feels like a marketing skin and the product feels like a generic dashboard.

## Propagation — 90 to 180 minutes

Lock `DESIGN.md`. Create shared tokens and primitives. Apply page-specific expressions by user responsibility. Do not invent a new visual identity for every route. Prioritize the routes that demonstrate the product’s value; mark lower-value surfaces as follow-up rather than pretending they are complete.

## QA — 30 to 45 minutes

Run the QA checklist at the agreed desktop and mobile widths. Test the primary happy path and at least one failure path. Verify direct route loading, loading/empty/error states, focus, contrast, mobile overflow, and any claimed persistence. Return screenshots and known limitations.

## Time-boxed decision rules

| Situation | Decision |
|---|---|
| Reference analysis is taking too long | Keep three strong references and document the rest as optional |
| Three concepts are too similar | Stop and change composition, not just colors |
| The hero is beautiful but the workflow is generic | Reject the direction and rebuild the two-surface proof |
| A library effect is tempting but unexplained | Do not use it until a product reason exists |
| A route cannot be finished safely | Ship the core proof and mark the route unverified |
| Backend behavior is unclear | Do not fake persistence; use an explicit fixture or stop |
| The palette feels attractive but harms readability | Choose legibility and semantic contrast over trend |

## Minimum viable premium delivery

A strong hackathon delivery has one ownable visual world, one memorable metaphor, one polished entry surface, one complete real workflow, a coherent `DESIGN.md`, responsive proof, honest functional states, and a concise evidence report. It does not require every route to have equal richness on the first pass.

## Final command to the agent

> Optimize for rapid, high-quality execution by reducing rework, not by skipping art direction. Time-box the concept gate, build the entry surface and core workflow first, lock the design system, propagate only after screenshot review, and report anything unverified honestly.
